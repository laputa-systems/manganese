# Manganese requirements

**Status:** frozen, manifest version 1, 2026-11-24. Changing anything here needs an owner decision and a new manifest version, which regenerates the affected goldens. The executable plan is [the roadmap](roadmap.md); how parity is proven is [the oracle](oracle.md); the consumer's frozen interface is [the appliance contract](appliance-contract.md).

**North star:** Build Manganese, exactly the browser functionality the appliance requires, as one Rust application ELF per architecture (Linux aarch64 and x86_64), with embedded resources and musl as its sole runtime library, built by Cargo from a pinned toolchain and vendored inputs. No permanent non-Rust implementation dependency other than musl itself. No external shared objects, dynamically loaded implementation modules, external executables, system packages, or runtime resource packs. Preserve the real browser, security and automation capabilities of the reduced appliance, and its page-observable persona. Use the frozen Hydrogen build as an executable differential oracle. Preserve Chromium's mature core architecture while replacing as much retained implementation as possible with vendored Rust software. This campaign optimizes for complete Rustification and functional, security and persona correctness with minimum new implementation work, not for browser runtime efficiency. Developer iteration speed is in scope, and it is bought with owned tooling (kache, Smolith, stuff), not by tuning the browser.

**Method and order (owner, 2026-11-24).** Requirements freeze at the Hydrogen the appliance runs in production on the freeze date. Chromium is only the oracle and is never patched to call Manganese code. Each Chromium subsystem becomes a golden black box at a seam Chromium already has, and a Manganese crate hill-climbs to parity against that box's goldens. Oracle testing comes first and integration last, assembled bottom-up as Rust-only builds. Tooling and the oracle come first; then leaf libraries, browser services, platform, graphics and compositing, Blink, and V8 at the very end. Nothing reaches the appliance until the assembled Rust browser passes the appliance contract. The objective is to port the reduced Chromium appliance, not to translate every line of Chromium or build a general-purpose alternative browser. Prefer deletion of unused paths, shared Rust implementations and upstream-quality improvements to existing projects over greenfield code. The handwritten inventory must be reconciled against the actual retained graph.

**Names.** Manganese is the Rust reimplementation of the reduced Chromium browser: a custom Chromium-derived browser, not a general-purpose alternative engine. Hydrogen is the qualified native Chromium-derived browser (ungoogled Chromium 156.0.8078.79, product id `chromium`, executable `chrome`) that the appliance runs today, that Manganese replaces, and that serves as its differential oracle. The **frozen oracle** is Hydrogen as the appliance runs it in production on the freeze date: the package revision 2 archive per architecture, plus its build tooling frozen in `oracle/build/`. A **golden box** is one oracle subsystem behind a seam, with a corpus, the oracle's recorded outputs and a comparator (U15). The **appliance** is the consumer: a VM per browser session whose guest kernel implements the subset of the Linux ABI Hydrogen uses, with a Rust supervisor that launches the browser, relays CDP and egress over vsock, and, in headed sessions, a remote Wayland compositor. Obligations are stated against Manganese; references to Hydrogen are to the oracle unless labeled otherwise.

## Product boundary

### What the executable must be

- One release ELF per architecture (`aarch64-unknown-linux-musl`, `x86_64-unknown-linux-musl`) with a Rust-owned browser implementation and immutable resources embedded in the executable. Owner, 2026-11-24: `chrome` is a musl-dynamic PIE whose only program interpreter is musl's loader (`/lib/ld-musl-<arch>.so.1`) and whose only `DT_NEEDED` entry is musl libc (`libc.musl-<arch>.so.1`). A static PIE segfaults when the appliance runs it through musl's loader, which one production image builder does (`ld-musl-x86_64.so.1 /opt/browser/chrome --version`), so a static executable would not be a drop-in.
- A real multiprocess browser: browser, renderer, zygote, GPU/software graphics, network, utility, crash/diagnostic and other retained roles can re-execute the same ELF with typed role selection. A single binary is not a single process. Keep unprivileged identities, separate address spaces, site isolation, sandboxing, and privilege boundaries. The appliance's actual process shape differs by mode: headless launches with `--in-process-gpu` and `NetworkServiceInProcess2`, so the GPU and network services run inside the browser process; headed runs a separate GPU process (`--use-gl=angle --use-angle=swiftshader --disable-gpu-compositing`) and the default out-of-process network service (`guest/appliance/src/browser.rs`). Owner, 2026-11-24: Manganese keeps the GPU and network services in separate processes in both modes, so the appliance's headless `--in-process-gpu` and `NetworkServiceInProcess2` switches have no Manganese equivalent.
- Manganese replaces the Hydrogen archive in the appliance's production images without any change to the appliance (owner, 2026-11-24). The executable contains browser roles only. The appliance supervisor and its remote Wayland compositor are environment, specified by the appliance contract, not Manganese roles.
- Use the appliance kernel's Linux ABI under libkrun/HVF/KVM in production; use native Linux and the full Linux guest as controls. The appliance kernel, the host kernel, VMM, host control daemon, host dashboard, RFB transport endpoint, host DNS/egress policy, and persistent disks remain outside the **guest executable's** implementation closure. They are explicit platform interfaces, not permission to outsource web-engine or graphics implementation to a native helper.
- Manganese delivers the archive the appliance contract defines; the appliance builds its own image from it. The production image has no distribution, shell, package manager, service manager, desktop environment or application sidecar programs; besides the archive it provides only musl's loader and libc. Mutable user profiles, downloads, temporary files, and configuration supplied by the appliance remain legitimate data.

- **Reference-build asymmetry (close in M0).** `oracle/build/scripts/generate-gn-args.py` makes the `chromium-wayland-release` profile differ by architecture in only these ways. arm64 sets `enable_swiftshader=true` and disables GLib, GIO, udev, system libffi and system minigbm. amd64 sets `enable_swiftshader=false`, keeps those system libraries, and stages Mesa (`libEGL`, `libGLESv2`, `libgbm`, `libgallium-*`, DRI drivers) from the builder (`oracle/build/scripts/stage-runtime.py`). Both architectures set `use_vaapi=false` and link Chromium's bundled FFmpeg statically into `chrome`. The system FFmpeg with its scoped libstdc++/libgcc closure and the host-libva VA-API path belong to the Helium amd64 profile and the headless product, not Hydrogen. arm64 also stages pure-musl NSS 3.133, NSPR 4.38.2, SQLite 3.53.4, expat, xkbcommon, zlib and libffi built from `runtime_sources.arm64` in `config/inputs.lock`. The packaged result: the x86_64 archive bundles 246 members, including Mesa's `libgallium-26.1.6.so` with `libLLVM.so.22.1` and its X11, ATK/AT-SPI, D-Bus, GLib and `libgcc_s` closure, while the arm64 archive's `lib/` holds only NSS, NSPR, SQLite, expat and xkbcommon, beside Chromium's own ANGLE, SwiftShader and minigbm libraries (`oracle/frozen/<arch>-r2/package-manifest.json`). Headed appliance sessions pass `--use-angle=swiftshader`, but the amd64 archive excludes `libvk_swiftshader.so`, and the Linux x86_64 qualification covered headless only. Which WebGL implementation, if any, x86_64 Hydrogen exposes in each mode is therefore unverified; M0 probes it on both architectures before any WebGL obligation is pinned. Do not treat the arm64 closure as the target graph on x86_64, and do not assume a Mesa exception in Manganese. The qualified reference keeps PartitionAlloc as malloc with BackupRefPtr (the frozen build's effective GN args; `oracle/build/scripts/verify-gn-args.py` does not assert it). Record that as the security baseline even where safe Rust ownership removes the need to port the mechanism.

Open product decisions are answered by small executable capability probes in milestone M0, not a broad research detour. If the evidence is inconclusive, retain the item as conditional and work on independent mandatory slices. Do not silently cut it. Never pretend a disabled or stubbed API works. Never treat a performance-oriented disabled flag as proof of nonreachability. No PDF, desktop or general Linux distribution expansion unless separately requested.

### Non-negotiable implementation and build policy

- All retained native implementation code is Rust. A Rust wrapper over C/C++, a port transpiled into a permanent foreign ABI, static archives containing legacy C/C++, runtime Wasm that executes a foreign implementation, a separate server/helper doing the same work, or `dlopen` of hidden modules does not count. Port the behavior, not the wrapper. Musl is the single intentional native-language exception; document the exact pinned musl/CRT/toolchain-supplied artifacts separately. The Rust compiler, its LLVM backend and linker are trusted build tooling, not shipped browser subsystems; LLVM embedded in a browser JIT or software rasterizer is **not** exempt. Rust implementations may contain reviewed unsafe code, intrinsics, and narrowly scoped Rust inline assembly; no separately compiled native algorithms. Do not confuse a Rust source tree with a Rust target closure.
- JIT-emitted machine code and compiler-generated machine code are necessary outputs, not source-language exceptions. Prefer Rust intrinsics; any unavoidable inline assembly inside Rust (e.g. syscall/architecture trampolines) must be narrowly audited, with no separately compiled non-Rust implementation source or opaque native objects other than the declared musl/toolchain boundary. Do not hide media or crypto implementations in assembly blobs. Unsafe Rust is permitted where justified and isolated; it is not a substitute for sound design.
- One vendored Cargo resolution/build graph and lockfile for Manganese, with explicit crate ownership and pinned sources. Preserve upstream source organization and separate upstream repos; do not flatten upstream code unnecessarily. Choose canonical common primitives early. Multiple versions and transitive runtimes are tolerated when changing them would slow functional progress; record exceptions and do not introduce overlapping direct dependencies without a demonstrated need. No general-purpose dependency-deduplication campaign. No system-library discovery, pkg-config, native implementation `-sys` shortcuts, CMake/Meson/autotools/GN/Ninja/Make as part of the final target build, npm/Node/Python/Perl orchestration, downloaded tools, network access, or prebuilt third-party implementation objects. Rust `build.rs`, proc macros and Rust-built generators are allowed when offline/deterministic and tied to declared inputs. Cargo may invoke the pinned compiler, standard library/linker and musl CRT. Toolchain provisioning and reference/test harnesses are separate.
- The release must be produced by `cargo build --release --locked --offline --target <musl-target>` (or an equivalently explicit Cargo-only invocation) from the vendored tree with a pinned toolchain already installed. No bootstrap scripts or `xtask` that secretly invoke a second build system. CI/reproducibility wrappers may verify, package, or run the binary but may not be required to compile it. Generators must work for clean builds or consume versioned, reproducibly generated source/data inputs with provenance.
- No external runtime implementation or immutable asset dependencies: no `.so`, `.pak`, ICU data file, V8 snapshot file, shader module, fonts directory, fontconfig cache/config, CA bundle, dictionary, filter-list seed, helper executable or locale file that must be installed beside the binary. Embedded web assets (HTML/CSS/JS), fonts, certificates and Unicode/codec tables are data or web content, not native-language implementation exceptions. Support user-supplied data and deliberate trust/profile configuration without turning it into a dependency on the host's distribution. Record licensing and update policy for embedded data.
- Zero foreign/native implementation exceptions formerly allowed by the appliance's earlier userland policy (Mesa, ALSA, NSS, browser archive, and FFmpeg descendant closures). Eliminate unnecessary features; replace or port the rest. Maintain a target graph and link/runtime evidence instead of relying on a source-extension count or a list of shared objects.
- These rules bind every Manganese crate from its first commit, not only the final release: each crate builds with `cargo build --locked --offline --target <musl-target>` and has no `-sys` or `cc` native build and no native transitive dependency. Chromium source, GN, Python and the oracle harnesses live under `oracle/`, build only the frozen oracle, and never enter the release workspace. The one exception is the test-only V8 bridge (E09), which lives outside the release workspace and is deleted in M7. Nothing links into Chromium, so Manganese pins its own Rust toolchain.

## Campaign philosophy: preserve the engines, reuse everything around them

### Owner-directed decisions

- **Keep Chromium, not a replacement browser.** Port Blink, including its document model, LayoutNG, style invalidation, event/lifecycle semantics and mature web API integration. Preserve V8's object representation, execution model, tiered JIT architecture, inline caches, feedback, speculative optimization, deoptimization, GC and embedding semantics. Preserve `content`, Mojo's trust/capability model, Viz/cc scheduling and site isolation. Implementation languages and internal library interfaces may change; these architectural assets are not dispensable simply because a Rust alternative exists.
- **No Servo or Boa engine substitution.** Servo, Stylo, Blitz, Boa, Nova, Argus, Wasmtime and other projects are legitimate sources of individual components and prior art. Do not replace Blink's DOM/layout engine wholesale with Servo/Blitz, or V8 with Boa/Nova or an interpreter-only runtime. Reuse parsers, code generators, regexp, Wasm or compiler primitives where they fit. A limited test harness or temporary porting scaffold is not a product engine or final dependency exception.
- **Reuse first, but not at the expense of a fundamentally weaker core.** Prefer existing implementations with credible functional coverage, clear ownership and acceptable security. For leaf subsystems, a slower but correct and reasonably complete crate is welcome. For core subsystems, retain the mature upstream algorithm and architecture even if the first Rust port is slower. No requirement to reproduce C++ internal APIs, bytecode encoding or incidental structures if an adaptation preserves architecture and observable semantics.
- **Tooling first, hardest ports last (owner, 2026-11-24).** Improving owned tooling is a higher priority than early engine progress. The first milestones build the frozen oracle, the golden store and the iteration lanes on kache and Smolith, and every later milestone exercises them. Port order runs from leaf libraries to services, then platform, graphics, Blink and finally V8. Do not start Blink or V8 ports early to de-risk them; record seams found along the way instead.
- **Frozen requirements, oracle first, integration last (owner, 2026-11-24).** The frozen oracle and the M0 manifest are the requirements. Changing either needs an owner decision and a new manifest version, which regenerates the affected goldens. Production Hydrogen may keep evolving elsewhere; that never moves the oracle. Every subsystem is first a golden box with a Rust crate hill-climbing to parity. Integration then runs bottom-up as Rust-only assemblies that are golden boxes themselves.
- **Persona parity (owner, 2026-11-24).** Wherever a page or server can hash or measure an output, Manganese reproduces the frozen oracle exactly (F16). This overrides reuse-first for those outputs: a reused crate is accepted only when its box is exact, and otherwise the native algorithm is ported mechanically.
- **Process model and profiles (owner, 2026-11-24).** GPU and network services stay in separate processes in both modes; in-process operation is a regression. Hydrogen profiles open in Manganese unchanged, so Chromium's SQLite and LevelDB formats stay.
- **Optimize for campaign completion, not browser efficiency.** No performance parity, startup, throughput, RAM, binary-size, energy or microbenchmark goals for the browser; no PGO tuning, allocator shootouts, SIMD tuning or broad code cleanup. Developer build and test turnaround is the one speed target, pursued through tooling (T16). Centralization that eliminates a duplicate port or supplies a shared interface is in scope; deduplication for aesthetics or dependency counts is not. Preserve V8 tiered JIT, mature layout algorithms and correctness-critical concurrency. Real hangs, deadlocks, unbounded resource exhaustion or operations that cannot finish remain correctness bugs. Adjust test timeouts and guest resources transparently for the first port.
- **Mechanically translated Rust is acceptable.** Translate mature C/C++ algorithms faithfully when no good substitute exists. C-shaped structs, straightforward unsafe Rust, temporary compatibility types, extra copies, broad crate boundaries and unidiomatic code are acceptable. Preserve explicit invariants and validate unsafe ownership, threading, aliasing and bounds; memory-unsound code is not excused by a mechanical port. Improve ergonomics and optimize later.
- **Owned projects first (owner, 2026-11-24).** Dogfood and improve the owner's projects: kache (build cache), Smolith (runtime, HTTP, WebSocket), img (image codecs, in place of zune and other image crates), play's vendored Symphonia, `ruopus` and `rusty-aac` (audio decoding, in place of upstream Symphonia), stuff (artifact store) and the Laputa forks in the registry. A gap in one of them is fixed there first, then pinned here.
- **Vendor, extend, upstream.** Select existing coherent Rust projects first, with the curated registry below as the default. Use Laputa-maintained forks wherever they already provide the functionality. Co-develop missing general-purpose features, portability fixes and native-dependency removals in their owning repositories, pin the validated revision in Manganese, and avoid application-local forks of already-owned code. Prefer upstream-compatible APIs, regression witnesses and tests. Native-backed default features must be disabled or replaced. No permanent foreign-code implementation is allowed.
- **Preserve the exact reduced product.** No mandatory full desktop browser, new browser API, hardware driver, PDF or printing implementation. Do not remove software WebGL, required media, security features or CDP simply because these are difficult. Where multiple native stacks serve one capability, replacing their required behavior with one Rust stack is permitted; do not port unused implementations solely to reproduce names in the source tree.
- **One Cargo closure and shared foundational services, not a global rewrite.** Default to Smolith, the Laputa Rustls/Graviola/webpki stack, existing Wayland/text/compression forks, and a single browser-facing abstraction per capability. Preserve Chromium sequence/task affinities; do not replace the JavaScript event loop, compositor threads or blocking/specialized execution with indiscriminate async tasks. Existing vendored libraries may keep their internal types and runtime when a change would delay progress. No new generic abstraction or forced rewrite just to standardize types. Generators must be Rust under Cargo or checked-in reproducible generated source/data.

### Disposition policy for each implementation node

| Disposition | When to choose it | Required proof |
|---|---|---|
| Reuse | Existing Rust implementation covers the needed leaf or subsystem | Actual required feature use, Cargo graph, native-object audit, differential tests |
| Extend | Rust implementation lacks a bounded set of necessary features or has removable native leaves | Concrete gap list, vendored patch, regression witness, final Rust closure |
| Extract | Larger upstream Rust project contains a reusable component, but adopting the whole architecture would be harmful | Explicit boundary, extracted sources/provenance, compatibility and security tests |
| Mechanically port | Chromium/native reference contains a mature implementation with no adequate Rust equivalent | Faithful behavior and invariants, upstream provenance, differential regression corpus, pure-Rust code |
| Remove | No retained capability requires the implementation | Graph/link absence, explicit product decision and correct unsupported behavior |

A candidate is not accepted because it compiles, wraps a native implementation, advertises a feature, passes a toy demo or has a Rust package name. Test actual required behavior and audit the selected feature graph. Prefer the named canonical family first; a second candidate is only a fallback when the primary fails a concrete requirement, not an invitation to run a lengthy bake-off. Reuse before porting, port before inventing, and remove only with a capability disposition.

Centralize common dependencies when it avoids implementation work or drift; leave optimization and cleanup for a separate campaign. Real hangs, crashes, security issues and failed workflows remain blockers.
- [ ] **U13 — Release closure sign-off.** Independent review of the complete source/build/link/runtime inventory, feature exclusions, all exceptions (musl/toolchain only), the musl-only artifact, Cargo invocation, conformance and appliance contract conformance. No open unclassified dependency or undocumented loss of retained behavior.

- [ ] **U14 — Milestone receipts and dependency refresh.** For each accepted milestone record native oracle revision, candidate source and vendored dependency pins, exact build/test commands, digest(s), retained-feature results, unsupported cases, negative tests, closure delta and remaining blockers. Do not invalidate a qualified dependency by refreshing its pin silently; rerun consumer witnesses after owner-fork changes. 
- [ ] **U16 — Persona surface report.** A repeatable report that captures build identity, every F16 surface and the required feature results, and diffs them against the frozen oracle on each architecture. Any unapproved difference fails it. It gates M8 and every manifest version change. 
- [ ] **U17 — Oracle equivalence.** Golden capture uses rebuilt and instrumented builds, so tie them to the product. A clean rebuild from `oracle/build/` must agree with the frozen x86_64 archive on every surface the M0 inventories record (persona, capability probes, CDP trace, ABI census) and on the frozen `test-fast`. Each capture-hook batch must leave the enclosing behavior unchanged with hooks enabled and disabled. Every box's anchor check (U15) must pass before its goldens are trusted. A rebuilt or instrumented oracle has its own immutable identity, and its discrepancies from the frozen archive are recorded and never mixed silently into receipts.
- [ ] **U15 — Golden box framework.** One spec per box under `boxes/`, declaring: the seam and its real call protocol (streaming, re-entrancy, callbacks, threading); a versioned wire protocol spoken by both the oracle harness and a thin Rust adapter; corpus sources; the environment inputs that affect the answer (architecture, CPU dispatch level, locale, timezone, fonts, data versions, feature flags); which outputs compare exactly, and the observable surface that justifies each exact comparison; which values legitimately vary and the relationships checked instead; which orderings matter (causal order, not incidental scheduling); expected oracle defects and required improvements, each with its own absolute assertion; the anchor check that ties the harness to the frozen archive through a public surface, or the reason none exists; and the arm64 evidence path (pinned arm64 captures, public APIs of the frozen arm64 browser, a narrowly scoped arm64 harness, or an arm64 assembly boundary). Before any candidate is compared, the oracle harness must agree with itself across repeated runs and processes. Goldens are immutable and content-addressed outside git, with digests in `goldens.lock`. Each box has a ratcheting scoreboard that fails on any regression, a holdout corpus the hill-climbing lane never sees, and a differential-fuzz lane against the live oracle harness. A holdout case that exposes a failure moves to the regression corpus once fixed, and the holdout is replenished with fresh items or fresh fuzz seeds so it stays unseen.

### Registry rule

For each key, name one owner and one primary implementation. Prefer the Laputa fork and extend its generic API rather than add another application-local implementation. A vendor-internal duplicate is allowed if correcting it slows delivery; document it and move on. Do not introduce a competing direct stack to avoid fixing a bounded gap in the selected one. No new general-purpose “Manganese standard library” or alternate browser engine. The registry is revised only with a short evidence-backed decision: failed required test, native closure problem, security defect, or clearly lower implementation cost at a proven seam.

## Co-development and upstream contribution protocol

This campaign is also a way to improve the Rust ecosystem. Source projects are first-class owners, not read-only dependencies. In particular, Smolith already provides a useful seam and is a high-leverage target for reusable browser-driven improvements.

| Own the change in | Example admissible work | Keep out |
|---|---|---|
| Smolith | Caller-dialed SOCKS/TLS transport integration; general pool partition-key hooks; streaming/cancellation; RFC-compliant client WebSocket headers, subprotocols and optional compression; H2 validation/test gaps; a browser wire profile that reproduces Chromium's HTTP/1.1 header order and HTTP/2 framing choices; optional QUIC runtime integration if required | Chromium-specific cookie/Fetch/CORS policy, CDP session semantics, product authentication, generic API redesign for aesthetics |
| Graviola / Rustls / webpki | Missing required Web Crypto or QUIC primitives; explicit provider configuration; a browser handshake profile that reproduces BoringSSL's ClientHello; trust/verification semantics and no-native closure; portability tests | New speculative algorithms, performance tuning, lowering certificate protections |
| HarfRust / Swash / rust-fontconfig / Fontations | Real shaping/rasterization/fallback/WOFF2/sanitization defects and pure-Rust closure fixes, deterministic embedded font input | Whole desktop font discovery or font ABI compatibility not used by appliance |
| wayland-rs / kbvm / Tinyland | Required wire/input/clipboard correctness, remote-only compositor features and library role entry points, closure fixes | Physical-seat/hotplug/DRM support merely because upstream offers it |
| zlib-rs / rust-brotli / rawzip | Reproducible format/streaming/validation bugs or browser-required integration | Compression ratio or speed tuning |
| Media/image/storage/graphics project or maintained fork | Required format/profile bugs, native feature removal, missing bounded standards functionality, test vectors and portability | Rewrite of the library for preferred coding style, complete format suite expansion without witnesses |
| kache | Compiler-cache correctness and coverage the oracle and workspace builds expose: wrong hits, misses, unsupported compiler invocations, Chromium GN and rustc wrapping | Cache features no Manganese build uses |
| img | Pure-Rust image decoders and encoders exact with the oracle's libjpeg-turbo, libpng, libwebp, libavif/dav1d and Skia codecs; browser-required formats and malformed-input behavior | Optimizer and CLI features the browser does not use |
| play | Audio decoding in its vendored Symphonia, `ruopus` and `rusty-aac` made exact with FFmpeg's output; container and timing fixes | Player UI, video output and device sinks |
| Manganese | Browser semantics, Blink/V8 integration, CDP server, security/process model, application-specific adapters and final closure | Forking a mature generic implementation to hide work from its actual owner |

For each contribution:

1. Start from a pinned owning revision and a failing browser-derived regression or concrete dependency/build witness; reduce it to the smallest reusable test.
2. Make a minimal generally useful API or correctness change in that project/fork, preserve existing consumers and document any intentional API change. No broad optimization or refactor tangent.
3. Run the owner's relevant test/feature/portability gates, the new regression and Manganese's consumer test. For Smolith check the affected package and feature-resolved dependency policy; never force a new runtime or native provider. Carry architecture-sensitive cases on both ISAs as soon as available.
4. Land the tested change in the maintained owning fork according to its repository rules, and record commit, tests, provenance/license, security impact, and consumer pin. If external upstream review is needed, carry a minimal pinned fork patch and keep the campaign moving. Do not block on upstream release/publication. External publication or changes to unrelated projects are separate decisions; don't expose private browser traces, credentials or customer data.
5. Re-vendor the exact accepted revision, rerun consumer witnesses, update the ledger and integrate. Do not let Manganese's vendored copy become the only location of a generic fix. Avoid synchronized mass upgrades; refresh a dependency only for required work/security.

This is **upstream-first ownership**, not “upstream acceptance before progress.” Co-development is in scope, but only for features/correctness/closure required by Manganese. No general roadmaps for unrelated projects. Where repo write access, permissions, hardware or external maintainers are unavailable, retain a reproducible patch and test, state the blocker, and work on the next independent slice.

## Definition of done

The campaign is complete only when all of these conditions are supported by digest-bound evidence, on both target architectures:

| Gate | Required evidence |
|---|---|
| **Exact capability scope** | Versioned retained/excluded feature manifest; every retained feature passes its qualification; every exclusion has a removal or unsupported-behavior witness. |
| **Rust purity** | Source, generated-code, feature, target, build and link inventory; zero foreign implementation code/objects, including bundled and transitive components, with only explicitly bounded musl/toolchain artifacts. No native Mesa, NSS, FFmpeg, BoringSSL, V8, Skia, ANGLE, Dawn, SwiftShader, etc. implementation left. |
| **Cargo alone** | Clean offline build with only the pinned Rust toolchain and vendored tree, using Cargo; no prohibited build subprocess, system package, network fetch or hidden native object. |
| **musl-only ELF** | One architecture-specific application executable whose only program interpreter is musl's loader and whose only `DT_NEEDED` entry is musl libc (owner, 2026-11-24); it runs directly and through `ld-musl-<arch>.so.1`. No hidden loadable implementation module, helper ELF or required asset sidecar. |
| **Hermetic runtime** | Minimal root whose only libraries are musl's loader and libc, no sidecar resources, no external executables, no unexpected runtime mappings/file reads. Required mutable data and appliance kernel and platform interfaces are explicitly enumerated. |
| **Correct security** | Multiprocess isolation, sandbox, site/origin policy, proxy confinement, trust validation, profile isolation and CDP authority proven with positive and negative controls. |
| **Real appliance parity** | The [appliance contract](appliance-contract.md) plus the frozen client workloads: CDP clients, persistent profile, headless and real headed login/UI, text, images, media, software graphics and native adblock on both reference architectures; no unsupported feature misrepresented as functional. | 
| **Persona parity** | Every F16 surface matches the frozen oracle on both architectures: exactly where the manifest says exact, within tolerance elsewhere. The U16 persona surface report shows no unapproved difference. |
| **Portable and reproducible** | Native-architecture builds and execution for aarch64 and x86_64; the appliance kernel and native Linux evidence, independent reproducible builds and source/artifact provenance. |
| **Core architecture** | Blink and V8 remain architecturally recognizable; mature layout, style, JS execution/GC/JIT, IPC and compositing machinery retained or faithfully adapted. No whole-engine substitution or interpreter-only loophole. |
| **Reuse-first disposition** | Each retained implementation has a registry key or explicit disposition, source provenance, selected pin, and required test. Reusable fixes live in their owning repositories/forks where practical. Deviations from canonical direct dependencies have a concrete reason; vendor-internal Rust duplicates are not closure failures. |
| **Functional reliability, not efficiency** | Retained operations actually complete with declared resources and timeouts; correctness, lifecycle, isolation, and bounded failure are proven. No mandatory speed, memory, startup, size, energy, build-time, deduplication or performance-improvement gate. |

### Required closure report fields

Each inventory entry should have: stable TODO ID; primary milestone; actual Chromium/build nodes; owning subsystem and source repository; retained capability; target/host/data classification; disposition (reuse/extend/extract/mechanically port/remove); selected registry key and revision, exact features, fallback rationale if any; upstream regression/commit and Manganese pin; native/build/unsafe audit; oracle/qualification reference; artifact digest; unresolved gaps. Track primary dependency choices separately from tolerable vendor-internal duplicates. The machine-readable census, not this initial handwritten list, is the final evidence of exhaustiveness.

### Example final build and inspection contract

```sh
# On a clean host with the pinned Rust/musl toolchain provisioned.
cargo build --release --locked --offline --target aarch64-unknown-linux-musl
cargo build --release --locked --offline --target x86_64-unknown-linux-musl

# For each resulting guest executable (actual crate/binary name to be decided):
#   inspect ELF headers, program headers, dynamic tags, symbols and link map
#   assert PT_INTERP is musl's loader and DT_NEEDED is only musl libc;
#   run `chrome --version` directly and through ld-musl-<arch>.so.1
#   verify build subprocesses, inputs and transitive native object provenance
#   run the identical executable in headless, headed and guest-role tests
#   inspect runtime mappings, execs and file access in a minimal guest root
```

The inspection utilities and external Chromium reference harness are not shipped dependencies or alternative build systems. A passing `ldd` result alone cannot prove implementation-language purity, absence of dynamically loaded code, or embedded resource closure. Cargo success alone cannot prove the absence of C/C++ code linked by a build script.

## Explicit unresolved decisions and limits

- The complete GN/target/link/runtime census is not yet present. M0 is the first acceptance prerequisite; the current broad inventory and APK locks are not proof of target reachability. The prior Hydrogen r1 qualification and r2 recipe differ; pin the actual chosen artifact, not merely a branch tip. No implementation has been newly built or qualified by this document revision.
- The scope defaults are proposed campaign decisions, including production-appliance-only physical platform scope, host-owned DNS, conditional QUIC/HTTP3/WebTransport/RTC/WebGPU, narrow UI and no generic codec/storage parity. Mandatory software WebGL, JS/DOM/layout, media, CDP, security and real headed/headless workflows are not optional. Close remaining capability ambiguity with executable reference probes and owner decisions where needed; do not misreport an exclusion as support. The extension API set is fixed by the frozen extension suite (R05); login, WebAuthn, codec and optional API requirements remain to be verified.
- The selected families (especially Turso, tiny-skia's path to Skia parity, OxideAV, Rust-native AV1, shader/backend codegen, WebCrypto/QUIC providers and font sanitization) are primary **qualification choices**, not known drop-in replacements.
