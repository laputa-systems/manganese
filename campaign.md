# Manganese: hermetically closed Rust browser appliance

**Status:** proposed execution-ready campaign charter, curated dependency policy, dependency-ordered sequence and subsystem inventory · **Date:** 2026-11-24

**North star:** Build Manganese, exactly the browser functionality required by the bctl appliance, as a single, hermetically closed, statically linked Rust/musl executable on Linux aarch64 and x86_64, built entirely by Cargo. No permanent non-Rust implementation dependencies other than musl itself. No external shared objects, dynamically loaded implementation modules, external executables, system packages, or runtime resource packs. Preserve the real browser, security and automation capabilities of the reduced appliance. Use the existing qualified Chromium-derived Hydrogen as an executable differential oracle. Preserve Chromium’s mature core architecture while replacing as much retained implementation as possible with vendored Rust software. This campaign optimizes for reaching complete Rustification and functional/security correctness with minimum new implementation work, not for runtime or build efficiency.

This is the execution plan and authoritative campaign charter. The subsystem TODOs retain their existing stable IDs; the milestone graph assigns dependencies and integration gates, not estimates or deadlines. The objective is to port the reduced Chromium appliance, not translate every line of Chromium or construct a general-purpose alternative browser. Prefer deletion of unused paths, shared Rust implementations, and upstream-quality improvements to existing projects over greenfield code. Treat the native Hydrogen build as a behavioral oracle and a temporary migration harness, never as an acceptable final dependency. The handwritten inventory must be reconciled against the actual retained graph.

**Names.** Manganese is the Rust reimplementation of the reduced Chromium browser built by this campaign: a custom Chromium-derived browser, not a general-purpose alternative engine. Hydrogen is the qualified native Chromium-derived browser from chromium-build (product id `chromium`, executable `chrome`) that bctl runs today and that Manganese replaces and uses as a differential oracle. Reactor is the guest kernel (formerly called Hydrogen); bctl is the host control plane and workflow consumer. Campaign obligations are stated against Manganese; references to Hydrogen are to the oracle unless explicitly labeled otherwise.

## Product boundary

### What the executable must be

- One release ELF per architecture (`aarch64-unknown-linux-musl`, `x86_64-unknown-linux-musl`) with a Rust-owned browser implementation, statically linked musl and immutable resources embedded in the executable. Static PIE is preferred if supported by the Reactor ABI and security contract.
- A real multiprocess browser: browser, renderer, zygote, GPU/software graphics, network, utility, crash/diagnostic and other retained roles can re-execute the same ELF with typed role selection. A single binary is not a single process. Keep unprivileged identities, separate address spaces, site isolation, sandboxing, and privilege boundaries.
- The final guest executable also includes the existing Rust `bctl-guest` and Tinyland remote compositor as self-exec roles, preserving current trust and process boundaries. Import their code as libraries rather than rewrite them. Their integration into the same ELF is a final packaging task, not a prerequisite for engine porting. No rewrite of the already-Rust host bctl control plane; no requirement to include kernel or VMM material in the executable.
- Use Reactor's Linux ABI under libkrun/HVF/KVM in production; use native Linux and the full Linux guest as controls. Reactor, the host kernel, VMM, host bctl daemon, host dashboard, RFB transport endpoint, host DNS/egress policy, and persistent disks remain outside the **guest executable's** implementation closure. They are explicit platform interfaces, not permission to outsource web-engine or graphics implementation to a native helper.
- Scratch guest image: executable plus filesystem/mount structure and platform-required kernel material; no distribution, shell, package manager, service manager, desktop environment, dynamic loader, or application-level sidecar programs. Mutable user profiles, downloads, temporary files, and configuration supplied by bctl remain legitimate data. Reactor kernel sidecars/modules are not browser dependencies. No promise of a dependency-free VM or of a single-file disk image.

- **Reference-build asymmetry (close in M0).** The qualified profiles are not identical across architectures. arm64 uses Chromium's in-tree ANGLE/SwiftShader with no system GLib/GIO/udev/minigbm/VA-API and bundled FFmpeg; x86_64 disables SwiftShader, stages Mesa llvmpipe plus system libffi/GLib/GIO/udev/minigbm and system FFmpeg with a scoped libstdc++/libgcc closure, and compiles VA-API decode against host libva. bctl's arm64 and x86_64 images therefore exercise different software graphics stacks. Qualify retained WebGL, media and sandbox behavior against both references; do not treat the arm64 closure as the target graph on x86_64, and do not assume a Mesa exception in Manganese. The qualified reference also keeps PartitionAlloc as malloc with BackupRefPtr (CHB-22/BCTL-65); record that as the security baseline even where safe Rust ownership removes the need to port the mechanism.

Open product decisions are answered by small executable capability probes in milestone M0, not a broad research detour. If the evidence is inconclusive, retain the item as conditional and work on independent mandatory slices. Do not silently cut it. Never pretend a disabled or stubbed API works. Never treat a performance-oriented disabled flag as proof of nonreachability. No PDF, desktop or general Linux distribution expansion unless separately requested.

### Non-negotiable implementation and build policy

- All retained native implementation code is Rust. A Rust wrapper over C/C++, a port transpiled into a permanent foreign ABI, static archives containing legacy C/C++, runtime Wasm that executes a foreign implementation, a separate server/helper doing the same work, or `dlopen` of hidden modules does not count. Port the behavior, not the wrapper. Musl is the single intentional native-language exception; document the exact pinned musl/CRT/toolchain-supplied artifacts separately. The Rust compiler, its LLVM backend and linker are trusted build tooling, not shipped browser subsystems; LLVM embedded in a browser JIT or software rasterizer is **not** exempt. Rust implementations may contain reviewed unsafe code, intrinsics, and narrowly scoped Rust inline assembly; no separately compiled native algorithms. Do not confuse a Rust source tree with a Rust target closure.
- JIT-emitted machine code and compiler-generated machine code are necessary outputs, not source-language exceptions. Prefer Rust intrinsics; any unavoidable inline assembly inside Rust (e.g. syscall/architecture trampolines) must be narrowly audited, with no separately compiled non-Rust implementation source or opaque native objects other than the declared musl/toolchain boundary. Do not hide media or crypto implementations in assembly blobs. Unsafe Rust is permitted where justified and isolated; it is not a substitute for sound design.
- One vendored Cargo resolution/build graph and lockfile for the appliance, with explicit crate ownership and pinned sources. Preserve upstream source organization and separate upstream repos; do not flatten upstream code unnecessarily. Choose canonical common primitives early. Multiple versions and transitive runtimes are tolerated when changing them would slow functional progress; record exceptions and do not introduce overlapping direct dependencies without a demonstrated need. No general-purpose dependency-deduplication campaign. No system-library discovery, pkg-config, native implementation `-sys` shortcuts, CMake/Meson/autotools/GN/Ninja/Make as part of the final target build, npm/Node/Python/Perl orchestration, downloaded tools, network access, or prebuilt third-party implementation objects. Rust `build.rs`, proc macros and Rust-built generators are allowed when offline/deterministic and tied to declared inputs. Cargo may invoke the pinned compiler, standard library/linker and musl CRT. Toolchain provisioning and reference/test harnesses are separate.
- The release must be produced by `cargo build --release --locked --offline --target <musl-target>` (or an equivalently explicit Cargo-only invocation) from the vendored tree with a pinned toolchain already installed. No bootstrap scripts or `xtask` that secretly invoke a second build system. CI/reproducibility wrappers may verify, package, or run the binary but may not be required to compile it. Generators must work for clean builds or consume versioned, reproducibly generated source/data inputs with provenance.
- No external runtime implementation or immutable asset dependencies: no `.so`, `.pak`, ICU data file, V8 snapshot file, shader module, fonts directory, fontconfig cache/config, CA bundle, dictionary, filter-list seed, helper executable or locale file that must be installed beside the binary. Embedded web assets (HTML/CSS/JS), fonts, certificates and Unicode/codec tables are data or web content, not native-language implementation exceptions. Support user-supplied data and deliberate trust/profile configuration without turning it into a dependency on the host's distribution. Record licensing and update policy for embedded data.
- Zero foreign/native implementation exceptions formerly allowed by the bctl userland policy (Mesa, ALSA, NSS, browser archive, and FFmpeg descendant closures). Eliminate unnecessary features; replace or port the rest. Maintain a target graph and link/runtime evidence instead of relying on a source-extension count or a list of shared objects.

## Campaign philosophy: preserve the engines, reuse everything around them

### Owner-directed decisions

- **Keep Chromium, not a replacement browser.** Port Blink, including its document model, LayoutNG, style invalidation, event/lifecycle semantics and mature web API integration. Preserve V8's object representation, execution model, tiered JIT architecture, inline caches, feedback, speculative optimization, deoptimization, GC and embedding semantics. Preserve `content`, Mojo's trust/capability model, Viz/cc scheduling and site isolation. Implementation languages and internal library interfaces may change; these architectural assets are not dispensable simply because a Rust alternative exists.
- **No Servo or Boa engine substitution.** Servo, Stylo, Blitz, Boa, Nova, Argus, Wasmtime and other projects are legitimate sources of individual components and prior art. Do not replace Blink's DOM/layout engine wholesale with Servo/Blitz, or V8 with Boa/Nova or an interpreter-only runtime. Reuse parsers, code generators, regexp, Wasm or compiler primitives where they fit. A limited test harness or temporary porting scaffold is not a product engine or final dependency exception.
- **Reuse first, but not at the expense of a fundamentally weaker core.** Prefer existing implementations with credible functional coverage, clear ownership and acceptable security. For leaf subsystems, a slower but correct and reasonably complete crate is welcome. For core subsystems, retain the mature upstream algorithm and architecture even if the first Rust port is slower. No requirement to reproduce C++ internal APIs, bytecode encoding or incidental structures if an adaptation preserves architecture and observable semantics.
- **Optimize for campaign completion, not efficiency.** No performance parity, startup, throughput, RAM, binary-size, energy, build-time or microbenchmark goals; no PGO tuning, allocator shootouts, SIMD tuning or broad code cleanup. Centralization that eliminates a duplicate port or supplies a shared interface is in scope; deduplication for aesthetics or dependency counts is not. Preserve V8 tiered JIT, mature layout algorithms and correctness-critical concurrency. Real hangs, deadlocks, unbounded resource exhaustion or operations that cannot finish remain correctness bugs. Adjust test timeouts and guest resources transparently for the first port.
- **Mechanically translated Rust is acceptable.** Translate mature C/C++ algorithms faithfully when no good substitute exists. C-shaped structs, straightforward unsafe Rust, temporary compatibility types, extra copies, broad crate boundaries and unidiomatic code are acceptable. Preserve explicit invariants and validate unsafe ownership, threading, aliasing and bounds; memory-unsound code is not excused by a mechanical port. Improve ergonomics and optimize later.
- **Vendor, extend, upstream.** Select existing coherent Rust projects first, with the curated registry below as the default. Use Laputa-maintained forks wherever they already provide the functionality. Co-develop missing general-purpose features, portability fixes and native-dependency removals in their owning repositories, pin the validated revision in Manganese, and avoid application-local forks of already-owned code. Prefer upstream-compatible APIs, regression witnesses and tests. Native-backed default features must be disabled or replaced. No permanent foreign-code implementation is allowed.
- **Preserve the exact reduced product.** No mandatory full desktop browser, new browser API, hardware driver, PDF or printing implementation. Do not remove software WebGL, required media, security features or CDP simply because these are difficult. Where multiple native stacks serve one capability, replacing their required behavior with one Rust stack is permitted; do not port unused implementations solely to reproduce names in the source tree.
- **One Cargo closure and shared foundational services, not a global rewrite.** Default to Smolith, the Laputa Rustls/Graviola/webpki stack, existing Wayland/text/compression forks, and a single browser-facing abstraction per capability. Preserve Chromium sequence/task affinities; do not replace the JavaScript event loop, compositor threads or blocking/specialized execution with indiscriminate async tasks. Existing vendored libraries may keep their internal types and runtime when a change would delay progress. No new generic abstraction or forced rewrite just to standardize types. Generators must be Rust under Cargo or checked-in reproducible generated source/data.

### Disposition policy for each implementation node

| Disposition | When to choose it | Required proof |
|---|---|---|
| Reuse | Existing Rust implementation covers the needed leaf or subsystem | Actual required feature use, Cargo graph, native-object audit, differential tests |
| Extend | Rust implementation lacks a bounded set of necessary features or has removable native leaves | Concrete gap list, vendored patch, regression witness, final Rust closure |
| Extract | Larger upstream Rust project contains a reusable component, but adopting the whole architecture would be harmful | Explicit boundary, extracted sources/provenance, compatibility and security tests |
| Mechanically port | Chromium/native reference contains a mature implementation with no adequate Rust equivalent | Faithful behavior and invariants, upstream provenance, differential regression corpus, pure-Rust code |
| Remove | No retained capability requires the implementation | Graph/link absence, explicit product decision and correct unsupported behavior |

A candidate is not accepted because it compiles, wraps a native implementation, advertises a feature, passes a toy demo or has a Rust package name. Test actual required behavior and audit the selected feature graph. Prefer the named canonical family first; a second candidate is only a fallback when the primary fails a concrete requirement, not an invitation to run a lengthy bake-off. Reuse before porting, port before inventing, and remove only with a capability disposition.

- [ ] **S03 — Page and Target domains.** Preserve tab/window/target creation, selection, discovery, lifecycle, navigation, frame tree, document IDs, lifecycle events, popups, workers, OOPIFs, reload and browser close behavior. Correct target detach/reattach semantics.

- [ ] **S06 — Input / Emulation.** Implement mouse, touch and keyboard event dispatch, text insertion, scrolling, viewport/device metric overrides, locale/timezone where supported, user-agent controls, media emulation and permission controls; preserve genuine user input/activation semantics and no hidden hardware impersonation.
- [ ] **S07 — Network / Fetch / Security.** Implement request/response events and IDs, headers, response bodies, interception/continuation/abort, cookie access, cache control, certificate/security state, failure causes and worker/frame attribution. - [ ] **S08 — Screenshots and visual APIs.** Implement Page.captureScreenshot, crop/scale/viewport/full-page behavior, PNG/JPEG/WebP as supported, screenshot timing, visual stability, screencast if retained, and correct software renderer readback. Printing/PDF APIs remain explicitly unsupported.

### T. Resources, generated code and Cargo-only build closure

- [ ] **T01 — Workspace ownership.** One root Cargo workspace/resolution, one lockfile, one final executable, pinned vendored sources and explicit role boundaries. Preserve owning repo layouts and import as libraries/path dependencies; default canonical foundational services. Do not flatten or fork redundantly just to remove duplicate versions. Temporary native hybrid harnesses use separate non-release tooling and cannot enter the final target closure.
- [ ] **T02 — Dependency feature audit.** Audit actual feature-resolved target and host graphs on both ISAs; deny native implementation `-sys` features and foreign objects, including hidden build paths. Maintain canonical defaults and an exception ledger for necessary Rust-only duplicates/transitive runtimes. Explicitly disable native TLS/crypto, graphics, compression, media, storage and wayland features. Do not optimize dependency count.
- [ ] **T03 — Rust-only generators.** Replace GN actions and Python/Node/Perl/native generators for Mojom, Web IDL, DevTools protocol, feature flags, localization, shader/builtin definitions, Unicode/codec tables, resources and snapshots with Rust-built generators/proc macros or checked-in reproducible generated Rust/data. Make dependency and input tracking explicit.
- [ ] **T04 — Resource embedding.** Replace Chromium `.pak`/locale packs, ICU data, V8 snapshots, GPU/shader resources, fonts/fontconfig, CA roots, public suffix list, adblock lists, dictionaries and UI assets with versioned embedded bytes/tables. Choose deterministic compression and lazy decoding as appropriate; do not extract shared implementation libraries or executables at runtime.
- [ ] **T05 — Self-contained static linker contract.** Build both musl targets with static linking (including libc/CRT), no `PT_INTERP`, no dynamic `DT_NEEDED`, no runtime loader and no hidden native archives. A static PIE may have a relocation/dynamic segment but must not require an interpreter or shared libraries. Audit symbol/link maps and ELF sections, including LTO/generated objects.
- [ ] **T06 — Rust toolchain boundary.** Pin Cargo/rustc, standard library, musl target/CRT/linker and compiler-builtins support; explicitly identify compiler-supplied native artifacts versus product implementation. Ensure no Chromium clang, libc++, libunwind, libgcc, embedded LLVM, Fil-C runtime, C compiler or host tool is smuggled into the product build. If Rust standard-library rebuild is required, it must use Cargo and the pinned toolchain.
- [ ] **T07 — Eliminate old build systems.** Remove target reliance on GN/Ninja/Siso, CMake/Meson/autotools/Make, Chromium depot_tools/gclient, pkg-config, bindgen/Crubit C++ bindings, external SDK/sysroot search and dynamic-library staging. External source comparison/reference builds remain permitted solely as oracle tooling.
- [ ] **T08 — No hidden build subprocesses.** Trace the build process tree and network/filesystem access in a clean restricted environment. Permit only declared Cargo/Rust tooling, Rust-built generators and necessary toolchain linker execution. Reject `build.rs` that shells out to prohibited systems or downloads/prebuilds native implementation code.
- [ ] **T09 — Reproducibility.** Rebuild offline from the same vendored source and pinned toolchain on independent clean hosts; normalize timestamps/paths/build IDs and compare release digests. Disable PGO and optional optimization tooling that complicates Cargo-only builds unless already effortless and hermetic; no compile-time or artifact-size target.
- [ ] **T10 — Runtime immutability audit.** Run the binary in a minimal no-library filesystem with no dynamic loader, fonts, resource packs, CA files or shell; capture executable mappings, file reads and process execs across retained workloads. Allow only explicit kernel interfaces and mutable/profile/session data; prove no hidden runtime dependency.
- [ ] **T11 — One executable, all required roles.** Prove browser/renderer/zygote/network/GPU/utility/diagnostic and strict guest init/compositor roles come from the exact same digest; preserve independent process identity and privilege. No helper `.so`, embedded ELF extracted to a temp directory or auxiliary daemon allowed.
- [ ] **T12 — Release packaging.** Update chromium-build and bctl consumption contracts for the one binary, digest/acceptance receipt and minimal image layout; separate kernel/VM metadata from application closure. Preserve both architectures, clean upgrade and rollback and native Linux oracle execution.
- [ ] **T13 — Supply chain and licensing.** Maintain SBOM, provenance, vulnerability handling, vendored patches, font/data/codec licensing, redistribution notices and security update procedure for the complete graph; embed or package legally required notices as non-runtime documentation or data. No source ambiguity.
- [ ] **T14 — Vendor-only build receipt.** Record every crate revision and feature, checked-in generated input, local patch and embedded asset with provenance; audit vendored projects for build scripts, proc macros, optional native code, C-backed crypto/compression, FFI, prebuilt archives, and hidden dynamic loading. A build-only Rust tool is permitted only under the Cargo policy; reference harnesses and native oracles stay outside the product build.

- [ ] **T15 — Migration versus release lane.** Maintain pinned native oracle and temporary hybrid Rust/native test harnesses for incremental leaf substitutions and V8/Blink differential debugging; no native scaffold may enter the final release graph. In parallel keep a small Rust-only static self-exec browser skeleton building via Cargo from the start. Grow real vertical slices without hidden fallback. Track residual native dependencies by reachable capability, not lines translated. Delete all transitional bridges by final closure.

### U. Oracle qualification, security, functional reliability and completion evidence

- [ ] **U01 — Differential oracle matrix.** Keep pinned original Chromium-derived Hydrogen runnable on native Linux and Reactor; compare exact retained capabilities and workload inputs on each architecture/mode. Classify expected exclusions, upstream bugs and candidate regressions explicitly; no selective golden regeneration to hide failures.
- [ ] **U02 — Language/web conformance.** Integrate relevant Test262, V8 regression, WebAssembly spec and Web Platform Tests, CSS reftests and targeted Chromium regression fixtures; maintain a required subset and report remaining failures by feature rather than one misleading aggregate score.
- [ ] **U03 — Graphics/text/media conformance.** Collect retained WebGL/Khronos and WebGPU (conditional) conformance, image/font/layout goldens, media corpus, real fixtures and screenshot differences with documented tolerances. Require actual use of Rust implementations, not fallback to native reference paths.
- [ ] **U04 — Security differential.** Test native sandbox and site isolation, renderer privileges, malicious IPC, malformed web data, egress confinement, certificate and origin policy, profile isolation, CDP authorization and exploit mitigations. Include negative controls that fail if protection is disabled; run on both target architectures.
- [ ] **U05 — Fuzz and robustness.** Fuzz HTML/CSS/JS/Wasm, fonts, images/media, shader languages, XML, TLS/protocol parsers, storage and IPC. Run appropriate Rust safety tooling/sanitizers and deterministic regression replays; track crashes, hangs, OOM and invalid-state transitions.
- [ ] **U06 — Real workflow completion.** Use the existing bctl suite and representative navigation, JS, interaction, rendering, media, downloads, profile and crawl fixtures. Require actual completion and correct results in both modes. Relax test timeouts or guest resources transparently if the initial Rust implementation is slow; no performance parity or quantitative improvement gate.
- [ ] **U07 — Resource and failure correctness.** Check that retained workflows can run to completion with sufficient declared resources, that resource exhaustion produces defined failures, and that memory/process/file handles and profiles are cleaned up correctly. Test leaks, runaway allocation, descriptor exhaustion and renderer churn when they affect correctness. Binary size, RSS, density and allocation rate optimization are out of scope.
- [ ] **U08 — Diagnostic observability.** Keep enough local logging, counters and traces to distinguish a slow computation from deadlock, protocol failure, security violation or lost work. Record timing/resource evidence when necessary to reproduce a functional bug. Do not create a benchmark, energy, size or build-efficiency tuning campaign.
- [ ] **U09 — Long-running and stress acceptance.** Exercise large pages, repeated tabs, media, long Grab crawl, profile churn, concurrent sessions, shutdown races, low-memory, disk-full, adversarial workloads, guest restart and recovery; address known bctl reliability gaps without hiding browser errors behind retries. Include BCTL-113's roughly 35-minute headless Grab-crawl hang where CDP stopped answering, the session closed mid-message and guest footprint grew about 437 MiB/hour: a CDP-, lifecycle- or resource-exhaustion failure must be reproduced and fixed, not masked by longer timeouts.
- [ ] **U10 — Coverage accounting.** Tie each retained capability, dependency node and implementation TODO to an oracle/fixture, structural proof or explicit removal witness. Measure branch/path/workload coverage where useful; uncovered paths stay open and cannot establish an exhaustive runtime closure by sampling alone.
- [ ] **U11 — Final proof on both targets.** Bind all build, ELF, runtime, compatibility, security and conformance evidence to exact executable/toolchain/source/guest digests. Ensure tests ran on real aarch64 and x86_64, native Linux and production Reactor, with both headless and headed behavior.
- [ ] **U12 — Deferred quality work.** Record known performance and resource regressions or cleanup opportunities only if already observed. No new performance benchmarks, ratio, speed target or deduplication campaign. Centralize common dependencies when it avoids implementation work or drift; leave optimization and cleanup for a separate campaign. Real hangs, crashes, security issues and failed workflows remain blockers.
- [ ] **U13 — Release closure sign-off.** Independent review of the complete source/build/link/runtime inventory, feature exclusions, all exceptions (musl/toolchain only), static artifact, Cargo invocation, conformance and actual bctl integration. No open unclassified dependency or undocumented loss of retained behavior.

- [ ] **U14 — Milestone receipts and dependency refresh.** For each accepted milestone record native oracle revision, candidate source and vendored dependency pins, exact build/test commands, digest(s), retained-feature results, unsupported cases, negative tests, closure delta and remaining blockers. Do not invalidate a qualified dependency by refreshing its pin silently; rerun consumer witnesses after owner-fork changes.

## Curated implementation registry

These are **selected defaults**, not promises that they already pass the browser's conformance or static build requirements. The campaign first tests the selected implementation on the actual required seam, then extends its owning project. Fallbacks are conditional on a concrete failure, not parallel projects to build. Existing Laputa repository names and relevant source files are checked against their current branches; pin exact revisions in M0/M1. Third-party source descriptions and capabilities are leads, not executed qualification. Audit the actual features, `build.rs`, native objects, unsafe code and security behavior. Prefer existing Chromium Rust integrations over a fresh adapter when compatible.

### Registry rule

For each key, name one owner and one primary implementation. Prefer the Laputa fork and extend its generic API rather than add another application-local implementation. A vendor-internal duplicate is allowed if correcting it slows delivery; document it and move on. Do not introduce a competing direct stack to avoid fixing a bounded gap in the selected one. No new general-purpose “Manganese standard library” or alternate browser engine. The registry is revised only with a short evidence-backed decision: failed required test, native closure problem, security defect, or clearly lower implementation cost at a proven seam.

## Co-development and upstream contribution protocol

This campaign is also a way to improve the Rust ecosystem. Source projects are first-class owners, not read-only dependencies. In particular, Smolith already provides a useful seam and is a high-leverage target for reusable browser-driven improvements.

| Own the change in | Example admissible work | Keep out |
|---|---|---|
| Smolith | Caller-dialed SOCKS/TLS transport integration; general pool partition-key hooks; streaming/cancellation; RFC-compliant client WebSocket headers, subprotocols and optional compression; H2 validation/test gaps; optional QUIC runtime integration if required | Chromium-specific cookie/Fetch/CORS policy, CDP session semantics, product authentication, generic API redesign for aesthetics |
| Graviola / Rustls / webpki | Missing required Web Crypto or QUIC primitives; explicit provider configuration; trust/verification semantics and no-native closure; portability tests | New speculative algorithms, performance tuning, lowering certificate protections |
| HarfRust / Swash / rust-fontconfig / Fontations | Real shaping/rasterization/fallback/WOFF2/sanitization defects and pure-Rust closure fixes, deterministic embedded font input | Whole desktop font discovery or font ABI compatibility not used by appliance |
| wayland-rs / kbvm / Tinyland | Required wire/input/clipboard correctness, remote-only compositor features and library role entry points, closure fixes | Physical-seat/hotplug/DRM support merely because upstream offers it |
| zlib-rs / rust-brotli / rawzip | Reproducible format/streaming/validation bugs or browser-required integration | Compression ratio or speed tuning |
| Media/image/storage/graphics project or maintained fork | Required format/profile bugs, native feature removal, missing bounded standards functionality, test vectors and portability | Rewrite of the library for preferred coding style, complete format suite expansion without witnesses |
| Manganese | Browser semantics, Blink/V8 integration, CDP server, security/process model, application-specific adapters, guest integration and final closure | Forking a mature generic implementation to hide work from its actual owner |

For each contribution:

1. Start from a pinned owning revision and a failing browser-derived regression or concrete dependency/build witness; reduce it to the smallest reusable test.
2. Make a minimal generally useful API or correctness change in that project/fork, preserve existing consumers and document any intentional API change. No broad optimization or refactor tangent.
3. Run the owner's relevant test/feature/portability gates, the new regression and Manganese's consumer test. For Smolith check the affected package and feature-resolved dependency policy; never force a new runtime or native provider. Carry architecture-sensitive cases on both ISAs as soon as available.
4. Land the tested change in the maintained owning fork according to its repository rules, and record commit, tests, provenance/license, security impact, and consumer pin. If external upstream review is needed, carry a minimal pinned fork patch and keep the campaign moving. Do not block on upstream release/publication. External publication or changes to unrelated projects are separate decisions; don't expose private browser traces, credentials or customer data.
5. Re-vendor the exact accepted revision, rerun consumer witnesses, update the ledger and integrate. Do not let Manganese's vendored copy become the only location of a generic fix. Avoid synchronized mass upgrades; refresh a dependency only for required work/security.

This is **upstream-first ownership**, not “upstream acceptance before progress.” Co-development is in scope, but only for features/correctness/closure required by Manganese. No general roadmaps for unrelated projects. Where repo write access, permissions, hardware or external maintainers are unavailable, retain a reproducible patch and test, state the blocker, and work on the next independent slice.

## Execution sequence and dependency graph

### Scheduling policy

- Keep two artifacts from the outset: a pinned native Chromium-derived oracle (and temporary hybrid leaf substitution harness where helpful), and a **separate** Cargo-built Rust-only candidate skeleton. The hybrid lane can use existing C++/GN build machinery for reference/integration only; it never qualifies as the release. Avoid requiring hundreds of fully translated leaves before running the first Rust role. Never make native fallback transparent.
- Start the highest-risk work (V8/GC/JIT and Blink bindings/layout integration) immediately after the contracts are pinned; run it concurrently with reusable leaf-family work and static build foundations. Do not spend the first half of the campaign polishing low-risk codecs while the engine is still unproven.
- Build vertical slices end-to-end early: process boot → CDP → HTTPS → HTML/text → JS/DOM → screenshots → headed login → real media/graphics. Use a minimal true implementation at each slice; report missing capabilities explicitly. Do not confuse an early smoke with browser completion.
- The pinned Chromium source, reference fixtures, Rust interface contracts, vendor registry and feature manifest are shared. Each slice owns a narrow subtree/library and has one integration owner. Parallel agents work on disjoint ownership areas or versioned interfaces; merge small tested changes frequently, rebase at actual interfaces, and don't create 21 independent frameworks. Use the same fixture and receipt format.
- Use native Linux x86_64 as the initial integration lane (bctl already records native/KVM qualification there); build/run minimal aarch64 probes early and keep architecture-dependent work dual-target. Reactor qualification is part of every applicable vertical gate, not an end-of-campaign surprise. Final gates require both guest architectures and both modes; missing hardware is an explicit blocked verification, not an emulation-only pass.
- For each milestone, release-independent test/port work can start as soon as its interface and reference cases are known. The prerequisites below govern **acceptance/integration**, not a rule that an entire upstream subsystem must finish before any parallel work starts. Maintain one shared mainline, per-slice source pins, an explicit missing-capability registry and a no-regression check for already accepted functionality. Use owner-repo tests for generic library patches. No performance campaign, no optimization gate, no unbounded research loop.
- Each subsystem TODO below has a primary milestone assignment. A conditional TODO closes by removal with evidence or by required implementation. The milestone receipts are authoritative and must cite exact IDs closed; no percent based on line count or number of files translated.

### Agent execution contract

When resuming, load the accepted reference, current source/owner pins, milestone receipts and TODO status. Identify ready work with the highest downstream dependency leverage. Pick a bounded slice with a real reference test, implement/adopt/extend/remove, run relevant owner and consumer tests, record proof, then integrate. If blocked on hardware, scope or dependency review, record the specific missing evidence and pursue another ready slice. Do not create generic abstractions, duplicate selected stacks, spend compute benchmarking, re-open accepted capability cuts without evidence, or endlessly expand the candidate inventory. Maintain a short list of cross-cutting blockers (V8 heap/JIT, Blink bindings/layout, software WebGL, media formats, storage migration, Reactor ABI and build purity), assign ownership, and revisit them continuously.

### Largest irreducible obligations (start early)

- V8's tagged object layout, GC/rooting, builtins, JIT tiering/deopt/safepoints and JavaScript/Wasm embedding; a Rust parser or compiler backend is not a V8 replacement.
- Blink/Content DOM lifecycle, cross-heap ownership, WebIDL binding, LayoutNG/style invalidation, events, workers and navigation/process isolation; reuse parsers without changing the engine.
- Software WebGL's real shader execution, validation and raster semantics; Vello CPU is 2D, Naga is not a full graphics driver. The campaign may require substantial ports from SwiftShader/Mesa even after redundant backends are removed.
- Browser-level media/Fetch/storage/CDP integration and security: generic crates provide codecs, protocol engines and stores, not browser correctness.
- Porting generators and native runtime support without smuggling C/C++ through Rust bindings or `build.rs`. Cargo closure must be maintained from the first standalone Rust artifact.

## Definition of done

The campaign is complete only when all of these conditions are supported by digest-bound evidence, on both target architectures:

| Gate | Required evidence |
|---|---|
| **Exact capability scope** | Versioned retained/excluded feature manifest; every retained feature passes its qualification; every exclusion has a removal or unsupported-behavior witness. |
| **Rust purity** | Source, generated-code, feature, target, build and link inventory; zero foreign implementation code/objects, including bundled and transitive components, with only explicitly bounded musl/toolchain artifacts. No native Mesa, NSS, FFmpeg, BoringSSL, V8, Skia, ANGLE, Dawn, SwiftShader, etc. implementation left. |
| **Cargo alone** | Clean offline build with only the pinned Rust toolchain and vendored tree, using Cargo; no prohibited build subprocess, system package, network fetch or hidden native object. |
| **Static ELF** | One architecture-specific application executable, no `PT_INTERP` and no `DT_NEEDED`; no hidden loadable implementation module, helper ELF or required asset sidecar. |
| **Hermetic runtime** | Minimal root with no dynamic loader or shared libraries, no sidecar resources, no external executables, no unexpected runtime mappings/file reads. Required mutable data and Reactor/platform interfaces are explicitly enumerated. |
| **Correct security** | Multiprocess isolation, sandbox, site/origin policy, proxy confinement, trust validation, profile isolation and CDP authority proven with positive and negative controls. |
| **Real appliance parity** | The bctl-observable appliance contract above plus existing and expanded bctl acceptance: CDP clients, persistent profile, headless and real headed login/UI, text, images, media, software graphics and native adblock on both reference architectures; no unsupported feature misrepresented as functional. |
| **Portable and reproducible** | Native-architecture builds and execution for aarch64 and x86_64; Reactor and native Linux evidence, independent reproducible builds and source/artifact provenance. |
| **Core architecture** | Blink and V8 remain architecturally recognizable; mature layout, style, JS execution/GC/JIT, IPC and compositing machinery retained or faithfully adapted. No whole-engine substitution or interpreter-only loophole. |
| **Reuse-first disposition** | Each retained implementation has a registry key or explicit disposition, source provenance, selected pin, and required test. Reusable fixes live in their owning repositories/forks where practical. Deviations from canonical direct dependencies have a concrete reason; vendor-internal Rust duplicates are not closure failures. |
| **Functional reliability, not efficiency** | Retained operations actually complete with declared resources and timeouts; correctness, lifecycle, isolation, and bounded failure are proven. No mandatory speed, memory, startup, size, energy, build-time, deduplication or performance-improvement gate. |

### Required closure report fields

Each inventory entry should have: stable TODO ID; primary milestone; actual Chromium/build nodes; owning subsystem and source repository; retained capability; target/host/data classification; disposition (reuse/extend/extract/mechanically port/remove); selected registry key and revision, exact features, fallback rationale if any; upstream regression/commit and Manganese pin; native/build/unsafe audit; oracle/qualification reference; artifact digest; unresolved gaps. Track primary dependency choices separately from tolerable vendor-internal duplicates. The machine-readable census, not this initial handwritten list, is the final evidence of exhaustiveness.

### Example final build and inspection contract

```sh
# On a clean host with the pinned Rust/musl toolchain provisioned.
cargo build --release --locked --offline --target aarch64-unknown-linux-musl
cargo build --release --locked --offline --target x86_64-unknown-linux-musl

# For each resulting guest executable (actual crate/binary name to be decided):
#   inspect ELF headers, program headers, dynamic tags, symbols and link map
#   assert no PT_INTERP and no DT_NEEDED
#   verify build subprocesses, inputs and transitive native object provenance
#   run the identical executable in headless, headed and guest-role tests
#   inspect runtime mappings, execs and file access in a minimal guest root
```

The inspection utilities and external Chromium reference harness are not shipped dependencies or alternative build systems. A passing `ldd` result alone cannot prove implementation-language purity, absence of dynamically loaded code, or embedded resource closure. Cargo success alone cannot prove the absence of C/C++ code linked by a build script.

## Explicit unresolved decisions and limits

- The complete GN/target/link/runtime census is not yet present. M0 is the first acceptance prerequisite; the current broad inventory and APK locks are not proof of target reachability. The prior Hydrogen r1 qualification and r2 recipe differ; pin the actual chosen artifact, not merely a branch tip. No implementation has been newly built or qualified by this document revision.
- The scope defaults are proposed campaign decisions, including production Reactor-only physical platform scope, host-owned DNS, conditional QUIC/HTTP3/WebTransport/RTC/WebGPU, narrow UI and no generic codec/storage parity. Mandatory software WebGL, JS/DOM/layout, media, CDP, security and real headed/headless workflows are not optional. Close remaining capability ambiguity with executable reference probes and owner decisions where needed; do not misreport an exclusion as support. The exact extension/login/WebAuthn/codec/optional API requirements remain to be verified.
- The selected families (especially Turso, Vello CPU, OxideAV, Rust-native AV1, shader/backend codegen, WebCrypto/QUIC providers and font sanitization) are primary **qualification choices**, not known drop-in replacements. Software WebGL, V8/GC/JIT and Blink binding/layout are substantial irreducible ports. No claim that all needed features or Cargo-only musl closure already exist. The exact foreign source/assembly boundary, Rust toolchain and runtime assets must be audited.
- QUIC/HTTP/3, WebTransport and WebRTC transport stay deferred. bctl's documented guest has no general UDP or QUIC path and egress is host-resolved SOCKS5 CONNECT over TCP; the opt-in H.264 dashboard viewer is host-side and not promoted. Quinn/h3, WebTransport datagrams and the host datagram relay in N06/M9 remain conditional on an explicit owner requirement, not documentation parity or a hypothetical capability.
- The strict single executable includes existing Rust guest supervisor and remote compositor roles; kernel, VMM and host services remain platform boundaries. Confirm this packaging interpretation before changing the existing bctl/chromium-build consumption contracts; the browser itself requires one-ELF closure regardless. Native Linux x86_64 is the proposed first integration lane, with aarch64 early gates and final dual-ISA acceptance; this is a scheduling choice, not a portability relaxation.
- Upstream co-development is a campaign design choice, not a record of commits made. Maintain vendor pins and reusable fixes in owning forks. External submission/review and unrelated changes are not required to complete Manganese. Repository access and hardware availability may block individual tests; record the blocker and continue on ready slices.
- No performance, memory, binary size, startup, throughput, compile-time or stylistic improvement target. Intentional early centralization reduces implementation work and maintenance duplication; general deduplication remains deferred. The final claim is complete retained-feature correctness/security and Rust/musl/Cargo closure, not competitive browser performance.
